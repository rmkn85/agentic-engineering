# Steer delivery

The existing coordinator acts as the Technical Delivery Lead. Continue toward the authorized outcome, not automatically along the same approach. This is a responsibility, not a mandatory additional agent or approval layer.

Load this procedure for substantial iterative work. Review before the next substantial batch and at meaningful iteration/commit, handoff, pause, resume, proposed completion, material scope/evidence change, recurring failure or allocation boundary. Do not wait for a commit while an uncommitted loop consumes resources. Coalesce adjacent events with unchanged evidence; do not trigger a new review solely because its own record was saved.

## Check, decide, act

1. **Recover authority and state.** Use the current task, requirements, owned changes, previous checkpoint and decisive evidence. Distinguish requirements from assumptions and implementation choices. Reassess a retained plan after resume without restarting valid discovery.
2. **Compare reality, not activity.** Identify verified capability, removed obstructions, decision-changing findings, regressions and new obligations. Compare both the latest increment and the principal user-outcome gap. Check whether the previous steering action was actually applied and what happened. A commit, passing local test or confident summary is not integrated acceptance.
3. **Account for investment.** Keep elapsed/waiting time, human effort, agent execution, tokens by available category/model, tool calls, expenditure and rework separate. Include review, coordination, context reconstruction and parallel workers. Inspect repeated changes to the same behavior or failed hypothesis, not just line counts. Unknown measurements stay unknown; use existing telemetry rather than building a tracker.
4. **Challenge the next action.** Would it still be justified from the current evidence without sunk-cost pressure? Consider removing unnecessary work, simplifying, changing the mechanism/order/owner, or a discriminating experiment. Preserve useful work. An overrun is not automatic failure; reproducible learning can justify persistence. Newly discovered uncertainty can be progress when it changes a decision.
5. **Decide and execute.** Choose CONTINUE, STEER, BLOCKED or COMPLETE. For actionable unfinished work, name the next bounded action, expected evidence and reconsideration condition. Revise forecasts when evidence changes them; a forecast is not a spending authorization. Preserve cumulative consumption and hard limits across task splits, new agents and resumes. Change soft allocations only within delegated discretion.
6. **Close the feedback loop.** Record the decision as specified below, replace the superseded next action in the existing task/handoff, and send material corrections to affected active workers through supported controls. Coordinate shared-contract changes through one owner. Verify adoption and effect at the next checkpoint. Do not stop at advice or request a routine user nudge.

## Authority and proportion

Choose implementation, sequencing, necessary supporting work, verification and executor changes within the existing contract and model/resource policy. Do not remove requirements, lower acceptance, add optional product scope, widen permissions or exceed owner limits. Escalate only the specific unresolved authority/value decision; continue independent authorized work. COMPLETE requires evidence for the requested scope and stops optional polishing.

Use one bounded independent reviewer for consequential ambiguity, conflicting evidence or repeated failure when fresh judgment can change the decision. Otherwise keep the review local. A solo agent's self-review is not independent. Evidence resolves disagreement, not vote count. Do not rerun unchanged checks or create a permanent committee.

## Decision record

Document every substantive checkpoint decision, including CONTINUE, in the existing task history or a coherent commit-message body. A routine continuation needs only its evidence, rationale and next check; reuse its reference across coalesced events. For a material change, include trigger/source identity, previous direction, evidence, concise decision rationale, the relevant alternative/tradeoff, uncertainty, resource/forecast change, new action/owner and expected check. At the next checkpoint append the observed effect linked to that decision: helped, not helped, mixed or unknown, with evidence. Do not rewrite the original rationale with hindsight.

Keep decision records out of source code, code comments, configurations and generated product artifacts. Do not create a parallel ledger or log-only commit loop. Link detailed tool evidence; do not copy private transcripts, credentials or raw dumps. If the normal record cannot be written, preserve it in an authorized task/handoff or commit route and report the missing persistence without claiming it succeeded.

[Record examples and adoption](../../docs/execution/delivery-steering.md) and [behavioral trials](../../experiments/delivery-steering.md) are optional detail. The procedure above is self-contained. This policy is an engineering hypothesis to evaluate, not proof of automatic invocation or measured savings.
