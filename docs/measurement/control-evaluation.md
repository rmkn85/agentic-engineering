# Evaluating a control change

Use this small offline evaluator when an owner needs a concrete adopt, revise, or inconclusive decision for a control change. It compares matched baseline and candidate observations under the same acceptance identity, task class, and model. It does not establish causality, supply universal thresholds, or gate ordinary delivery. The owner supplies every threshold in the input; a null threshold deliberately prevents a recommendation.

Run it with Python 3.9 or newer:

```sh
python tools/control_evaluation.py examples/control-evaluation/pilot.json
python -m unittest discover -s tools/tests -p 'test_control_evaluation.py'
```

Each observation has a pair ID, arm, fixed acceptance/taskclass/model/harness/conditions fields, outcome (`accepted`, `failed`, `unfinished`, or `cancelled`), authorization timestamp, and counters for rescue, rework, escaped defects, active seconds, and control seconds. Accepted outcomes require `accepted_at`; other outcomes forbid it. Optional `feedback_at`, `edit_at`, model usage, and top-level `now` preserve unknown values as null. Timestamps require an explicit timezone. With `now`, nonaccepted attempt ages are retained; failed candidate outcomes prompt `revise`, while unfinished/cancelled candidates prevent adoption and remain visible in outcome counts.

The explicit policy fields are minimum matched pairs, desired leadtime reduction fraction, desired rescue reduction fraction, maximum escaped-defect increase, maximum control-overhead fraction, and `intentional_differences`. The latter may name `harness` or `conditions` only when the owner deliberately varies that dimension; acceptance, task class, and model must always match. Leadtime and rescue reductions are computed from pair-matched accepted durations and rescue counts, divided by the respective baseline median. A zero or unavailable baseline denominator makes the ratio unknown. Control overhead is candidate control seconds divided by candidate active seconds; each observation must also satisfy control seconds less than or equal to active seconds; zero over zero is measured as zero. The input rejects positive control with zero active seconds because it violates the control-less-than-or-equal-to-active invariant. Unknown required evidence cannot be treated as zero or as a pass.

Output reports matched and unmatched pairs, confound mismatches, all attempt outcomes and nonaccepted attempt ages, accepted authorization-to-acceptance leadtime and edit-to-feedback latency separately, rescue and defect differences, control overhead, optional model usage, and candidate nonaccepted age. Pairs with mismatched acceptance identity/task class/model or undeclared harness/conditions are excluded from matched calculations and listed. Any incomplete metric uses the full eligible matched population; it is not calculated from a selectively smaller subset. An unmatched candidate blocks adoption. A candidate failed outcome, a known defect increase above owner policy, or a known unmet numeric criterion yields `revise`; insufficient matches, mismatches, missing criteria, or unknown required metrics yield `inconclusive`. `adopt` means only that these supplied criteria passed in this observed sample. Review the observations and acceptance evidence before acting; this tool does not determine whether the chosen criteria or recorded outcomes are valid.

This is a local calculation over supplied JSON only. It makes no network or model calls and stores no telemetry. It is intentionally not a statistical test or a general experiment platform. A result can be misleading if observations are incomplete, acceptance labels drift, task difficulty differs within a task class, or timestamps/counters are inaccurate. Keep failed, cancelled, unfinished, and unmatched work in the input rather than selecting only successful runs.
