# Bind outcome controls to the native delivery path

Use these controls where an unsupported completion claim, stale assignment,
lost checkpoint or disposable-resource leak is a real process risk. The existing
task, component owner, permission system and acceptance authority remain in charge.
The helpers are portable Python 3.9+ commands, not a scheduling service or a
replacement backlog. Simple tasks can retain their existing adequate route.

## Smallest complete installation

1. Keep the canonical task in its existing owner. Add the versioned
   [outcome-control extension](../execution/outcome-control.md) and declare required
   controlled tasks in the native frontier policy. Bind goal meaning, acceptance,
   rights, claim applicability and WIP policy before assigning the work. Protect
   that owner policy through the existing review/permission boundary.
2. Use the [native activities](../../tools/README.md#outcome-control-activities)
   at start/resume, before the affected write, before integration and before
   completion. Check actual paths and capability observations, not a remembered
   grant. Reconcile the canonical task through its existing atomic writer or the
   supplied compare-and-swap reference route. Do not place a successful check in
   one command and an unrelated unchecked write in another.
3. Have the actual native producer report the exact claim/scenario, source and
   loaded identity, positive completion, substantive verdict, errors and relevant
   conditions. Retain immutable hashed receipts outside the source identity they
   attest. The claim validator cannot turn a forged receipt into truth or measure
   human taste. Protect the producer and use an independent oracle.
4. Feed process observations through the [runtime controls](../execution/runtime-controls.md).
   The owning host dispatches a decision only on their meaningful-change output
   or a declared stall/heartbeat condition. Reconcile the previous decision's
   observed effect before admitting another substantial batch. Continue useful
   recovery/reduction when an admission limit is reached; do not silently renew
   limits or remove acceptance.
5. Preserve consistent checkpoints outside disposable execution state. Retire
   only exact owned, inactive resources after readback verification. Restore into
   a fresh owned destination, then recheck current authorization. Git worktrees
   use their native Git producer; generic scratch deletion must not replace it.
6. Put task validation and the affected negative controls in the repository's
   normal CI/finish route. A required controlled task must fail if its extension
   or validator disappears. Review adoption through an ordinary worker task,
   including stale context and negative evidence, rather than only loading files.

In this repository, `make check` runs the mechanism regressions and
`make control-trial` exercises the maintained command routes together. The cold
and stale contributor trial runs both through the native acceptance boundary.
Examples create original neutral fixtures; they are not product deployments.

## Trigger, owner and consequence

| Boundary | Native owner supplies | Executable consequence |
| --- | --- | --- |
| Authorization or policy changes | Reviewed current goal, rights, scope and acceptance | Old assignment/request/evidence digests fail; reassign and reopen affected claims |
| Start or resume | Current task/source/conditions, effective scoped capability receipt | Stale inputs, unknown/denied capabilities and inconsistent recovery fail |
| Source or task write | Actual planned paths, current task digest and valid proposal | Scope denial, concurrent/stale writes and unsupported task transitions fail |
| Native verification result | Claim/scenario-specific positive oracle and actual loaded identity | Exit-only, incomplete, rejected, wrong-source or wrong-class evidence cannot satisfy a claim |
| New substantial batch | Current constraint/decision, previous result evidence and projected WIP | Unreconciled prior outcome or exceeded admission limit blocks new work; authorized reduction/recovery remains possible |
| Telemetry event | Selected fields, meaningful critical signals and justified jitter | Unchanged incidents coalesce; new critical events and cumulative drift wake the owner |
| Integration/completion | Applicable prerequisites and independent evidence classes | Unsupported completion, absent required controls and mismatched acceptance fail native validation |
| Resource retirement | Exact owner/instance, stopped consumers, released lease, verified outside checkpoint | Shared/active/changed/unpreserved resources survive; safe scratch can be removed and restored |

The gates verify declared facts and bytes. They do not authenticate an arbitrary
JSON author's identity, discover unrecorded consumers, enforce OS permissions,
choose product priorities or replace intrinsically human acceptance. Those are
explicit responsibilities of the native owner and trusted producer. Protecting
policy and evidence production is part of installation, not a capability obtained
by setting a JSON field to true.

## Research-to-control coverage

The [research rationale](../../references/outcome-evidence-control-2026-11.md)
and [primary-source map](../../references/outcome-control-source-map.md) distinguish
empirical findings, documented practice, hypotheses and unresolved provenance.
Load them for methodology decisions; ordinary execution needs only the reached
procedure and native command.

| Failure family | Control and decisive check |
| --- | --- |
| Task selection | [Steering](../../skills/steering-delivery/SKILL.md) selects from the remaining user gap; the task loop retains expected versus observed effect. Behavioral trials test wrong-priority contrasts |
| Problem framing/architecture | Owner-bound authority, edit rights and claim policy preserve the agreed boundary; independent problem-first review remains judgment |
| Evidence semantics | Exact claim/scenario, completed native verdict and source/loaded identity; reject exit-zero, wrong source and receipt reuse |
| Acceptance layer | Required mechanical/expert/human classes; reject mechanical evidence substituted for required judgment |
| Knowledge state | Hash-bound recall coverage/continuation, condition-bound observations and stale-authority checks; reject missing pages and changed inputs |
| Harness/environment | Current scoped capability receipt with separate authorization and probe; reject denied/revoked/mismatched observations |
| Flow/resources | Owner-declared semantic WIP, recoverable task snapshots and verified resource retirement; exercise restore and admission/reduction contrasts |
| Measurement/incentives | Changed-state observation and complete lead/feedback intervals; retain failed, unfinished and unmatched attempts |
| Learning system | [Control evaluation](../measurement/control-evaluation.md) applies owner-chosen retain/revise criteria; missing evidence cannot produce an adoption recommendation |

## Adoption and retirement decision

Use the next existing authorized deliverable. Retain source revision, native
bindings, received instructions, first selected action, corrections, accepted
consumer result and control overhead. The [evaluation helper](../measurement/control-evaluation.md)
compares submitted matched observations under explicit owner criteria; it does
not establish causality or supply universal thresholds. A passing synthetic trial
does not prove a real host bound the gates, a model followed them, or a product
was accepted.

Keep controls that prevent relevant failures at acceptable total cost. Revise or
remove those that delay delivery, increase rescue work, duplicate authority or
need routine exceptions. Remove a binding only through its owning policy change,
preserving required evidence, permissions and unfinished checkpoints. Do not
disable a check merely to make the current candidate pass.
