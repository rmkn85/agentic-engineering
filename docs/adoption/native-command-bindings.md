# Bind shared guidance to executable native paths

Reviewed 2026-09-20. Evidence class: generalized practitioner lessons with discriminating local regression tests; not a completed cross-host or low-cost-model benchmark. Keep private source identities, incidents and host details with their original owners.

The [repository-only contributor contract](newcomer-contract.md) is an outcome: a capable newcomer can make the requested change through an existing accepted delivery path. Copying a handbook, validating its hash, or printing commands is not that outcome. Shared authorship should remove repeated infrastructure reasoning, not relocate it into another manual.

## Select by the actual process

Every maintained first-party repository needs source identity, preservation of existing work, bounded context, interruption recovery and honest evidence. Add procedures according to concurrent writers, composed packages, public delivery, large/private inputs or physical resources. The repository does not have to experience an incident first.

A dominant-language label, test-routing category or repository name is not an environment specification. Follow the actual package manifests, lockfiles, Make targets, scripts and their called dependencies. A mostly Python contract package may require a sibling's TypeScript compiler for its full checks; a task-management repository may use a pinned Node package even when its helper scripts are Python. These neutral examples describe dependencies, not permission to install an entire portfolio.

For each route, bind the working directory, native command, selected input/dependency owners, permitted effects and evidence boundary. Keep source acquisition, environment installation, small fixtures, private resources, service lifecycle and publication separate. Place an owner-specific exception beside the owner's template rather than growing a universal switch or giving a low-cost agent contradictory setup recipes.

## Sandbox-first external activities

Plan and complete everything the sandbox already permits before requesting broader access: source edits, inspection, fixtures, local builds/checks, command implementation and a reviewable non-mutating plan. Use authorized structured tools when they already provide the required activity. Identify the remaining external effect and why it cannot stay inside the sandbox; do not treat a failed broad command as evidence that every part needs escalation.

Bind a recurring external activity to a maintained parameterized Make target or strict Make-style wrapper. Review its implementation, allowed inputs, fixed destination/effects, failure/retry behavior and evidence before the first approval. Validate parameters as data and pass argument vectors without shell evaluation. Reject arbitrary commands, escaping paths, undeclared options/variables and extra goals. For example, CI retrieval accepts a validated repository/run/job identity and returns a bounded failure index with retained logs; it does not accept a shell snippet. Keep read-only logs/status separate from merge, deletion, deployment and configuration writes.

Ask once for the concrete activity and a narrowly scoped allowlist entry through the supported authorization process, then reuse it within scope. Do not request blanket `python`, shell, generic `make` or arbitrary `-C/-f/--eval` permissions. Prefer an absolute reviewed wrapper path plus activity prefix when the host cannot bind working directory; a relative `./tools/make` prefix alone can match a different repository's wrapper. A plain GNU Make prefix does not constrain additional goals/options, recipe overrides or mutable makefiles. The wrapper must reject them, and its maintained contents/transitive effects remain a trust boundary; a prefix rule does not attest their digest. A changed effect, permission or destination needs a new review, not silent expansion of the existing activity.

**Reject ad-hoc command approval requests automatically where native controls support it.** In the reviewed Codex [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference), granular `sandbox_approval=false` rejects sandbox-escalation prompts and `rules=false` rejects execpolicy prompt approvals; existing matching `allow` rules can still permit reviewed activities without prompting. The [rules contract](https://learn.chatgpt.com/docs/agent-configuration/rules) gives `forbidden` decisions precedence and documents prefix/shell parsing. Review these settings against the actual host and preserve unrelated permission categories. They reject prompt categories, not "inline" provenance: `request_permissions`, skill approvals and MCP elicitation have separate controls. Do not silently disable those or use them to obtain equivalent ad-hoc command access. Rule installation requires a separately authorized path when command prompts are disabled; the new command cannot authorize itself. Configuration/source inspection is not proof of effective live enforcement.

Never request escalation for inline scripts, heredocs, assembled shell expressions or a temporary script used to bypass the activity boundary. Moving the same code into `/tmp` does not make it maintained. When the named activity is missing, prepare its sandboxed implementation, tests and exact effect/allowlist proposal, then request that activity's approval or report the missing installation. Do not retry a rejected command through another permission surface or loosen the sandbox to avoid the route.

This repository's optional [Codex settings activity](../../tools/README.md) demonstrates the binding: `tools/make codex-settings-plan HINT_FILE=<private-file>` prepares a private digest-bound plan; `tools/make codex-settings-apply PLAN_SHA256=<digest>` applies only the reviewed routing-hint replacement and removal of the global compaction threshold at the fixed native destination. It preserves saved model/effort and unrelated settings. The activity requires Python 3.11+ for standard-library TOML validation and POSIX ownership/mode APIs. Plan first inside the sandbox, review the bounded changes, authorize the exact activity, then apply and read back. If the native approval did not persist its prefix, the separately approved `tools/make codex-settings-allowlist PLAN_SHA256=<digest>` installs only that fixed apply prefix in a dedicated rule file after verifying the applied settings result. Run installation from the intended stable checkout, not a retiring worker worktree. It preserves other rule files, refuses a differing dedicated file and never authorizes the installation command itself. This is not a generic permission broker, and file installation alone does not prove adoption by a running host. Keep private plans/backups outside the public corpus, retain necessary evidence and clean owned scratch after integration. Approval semantics reviewed **2026-10-18**; real-host acceptance remains separate from helper tests.

## Test the binding, then the journey

A rendering test should catch wrong runtime selection, missing owner-specific prerequisites, unresolved placeholders and details leaking into an unrelated owner. It must also include a simple task that does not need the full environment. A Make dry-run or printed setup plan verifies routing, not successful installation.

Then execute the real selected preparation from a cold cache, the changed behavior and the native integration boundary. Use the same native commands in CI. Confirm the exact candidate and accepted artifact, and verify delivery at the repository's real destination. Do not invent web deployment for a library or documentation repository. A successful root checkout does not prove every pinned sibling is the intended revision.

An explicit safe blocker is necessary when authority or a resource is missing, but it is not a passing newcomer trial. Repeated predictable blockers should become maintained provisioning or a pre-authorized execution route. Do not normalize a workflow that tells every feature contributor to perform the same infrastructure investigation.

## Maintain copied guidance without destroying local work

Extend the existing template/copy owner rather than creating another distributor. Ordinary feature work should not run organization-wide synchronization. A maintenance operation needs explicit selection, a non-mutating preview, a drift check and deterministic outputs. Record the reviewed upstream revision and exact copies separately from local adaptations.

Before applying the selected write set, verify actual repository roots and remote identities, reject escaping or symlinked destinations, and inspect every managed destination. Preserve differing staged, dirty, untracked and ignored files. Ignored content is not disposable; a clean Git status alone cannot authorize its overwrite. Do not create a pretend repository inside a missing sibling directory.

Only replace paths the distributor owns. Unknown rules are not stale merely because they are absent from its current template directory. Retire an obsolete rule through an explicit reviewed migration. Use per-file atomic replacement and recheck for changed content; repeated application should be a no-op. These mechanisms are not a distributed transaction or an atomic multi-process ownership lock. A partially interrupted multi-repository update needs recorded per-repository progress and the normal concurrency policy.

A verified source pin and hash detect drift, not correctness. Do not fetch latest shared policy on every task, overwrite an intentional adaptation, or update every consumer merely because an unrelated upstream research page changed. Preserve required local resources and keep product/task/permission authority local.

## Evidence that survives another interruption

Record the smallest useful result in the existing owner record: source and changed scope, exact executed checks, remote commit identity, relevant artifact/delivery identity, remaining failure and next executable work. Keep implemented, verified, integrated and delivered separate. A newer failed job may have a different first failure than yesterday's job; read its actual steps and decisive evidence before prescribing the old remedy.

Distinguish an original test failure from a later failure to upload its evidence. Preserve the first cause even when diagnostics or cleanup also fail. A retained success from another candidate is not a substitute. Keep raw logs retrievable where authorized, but expose compact structured facts first; never publish private logs into the public methodology repository.
