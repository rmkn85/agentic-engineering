# Portable contributor lessons — September 2026

Review date: 2026-09-19. Evidence class: qualitative practitioner synthesis and engineering hypotheses, with separately documented vendor behavior. This is not a controlled cross-model benchmark. Examples are re-authored and anonymized; no private repository excerpt, internal URL, raw log or workstation configuration is reproduced.

## Why sharing tips alone is insufficient

Independent projects often learn different aspects of the same contributor contract. One discovers that a published artifact differs from a tested source. Another discovers that individually passing packages fail when installed together. Another discovers that a desktop environment's hardware or native libraries cannot be assumed in a cloud job. These are not reasons to give each project only its own hard-won rule. They are reasons to model capabilities and apply the relevant protections before a failure repeats.

The expected benefit is less infrastructure reasoning, repeated context and recovery effort for the same authorized feature. The tradeoff is maintenance of small deterministic commands, local bindings and evidence. This claim should be evaluated on real newcomer tasks; no numerical saving is asserted.

## Generalized lessons and contrasting cases

| Lesson | Mechanism | Limit or counterexample |
| --- | --- | --- |
| A green component test is not connected behavior | Exercise the packed/installed caller-provider boundary with exact source pins | A wording-only change should not need every runtime |
| A successful publisher is not verified serving | Connect candidate, artifact, promotion and served identity | Libraries/docs may not have a public service to deploy |
| A stale instruction can be more harmful than no instruction | Refresh source identity and reload changed entry guidance | Do not reload unchanged history every turn |
| More prompt text does not ensure delivery | Test availability, native host delivery and actual behavior separately | A simple task should not load every skill |
| Repeated branch-head failures do not imply poor module design | Distinguish moving-head serialization from same-file contention | Real shared contracts still require coordination |
| Clean textual merges can be semantically incompatible | One authority for contracts and actual consumer tests | Avoid speculative compatibility layers for private young APIs |
| A failed CLI is not a global permission diagnosis | Check the actual available authorized route and exact failed operation | Do not hunt credentials or bypass denied policy |
| A warm machine hides undeclared prerequisites | Cold setup with locks and selected environment scopes | Do not install a whole portfolio for one package edit |
| One environment cannot model all evidence | Distinguish headless, rendered, replay, real-device and production evidence | Do not demand physical hardware for pure deterministic source tests |
| CI fallback can change the trust boundary | Pre-authorized runner classes, exact candidate and unchanged acceptance | Never send untrusted work into a personal account merely to save quota |
| A crash need not destroy continuation | Coherent remote checkpoints and compact existing task records | Do not invent a second distributed task ledger |
| Retaining evidence need not flood context | Summary, indexed structured evidence, then raw detail | Do not truncate away the only contradictory observation |
| Central guidance can become a new outage | Reviewed self-contained local snapshots with provenance | No fetch-latest instruction or submodule needed for ordinary work |
| Generic does not mean globally authoritative | Promote execution mechanisms, retain product and domain authority | A reusable planning method may still be outside this repository's scope |

## Research implications for adoption

The operating core should be common; additional procedures are selected by multi-repository composition, concurrent writing, public delivery, data/device needs, or expensive execution. Selection is not based on the originating project, agent brand or whether a failure already happened. A new project should inherit applicable protections immediately.

Conversely, adoption is not copying every manual. Keep a tiny entry route, local native commands and optional deeper procedures. Mechanical exact work belongs in ordinary tools. Trade secret histories and personal environment data do not belong in the public corpus; retain only the capability or constraint needed to explain a lesson.

A repository can automate its portion of onboarding, but an unauthenticated host cannot clone private source by reading a nonexistent local file. Account permission, base tools and execution policy are ingress prerequisites. Provision them once, report them precisely when absent, and never reinterpret them as authorization to weaken a sandbox.

## Authoritative behavior references

The links below document mechanisms, not successful installation in any particular editor. Recheck the selected host/version when adopting.

- OpenAI, [custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md): instruction discovery depends on scope/start location and the supported instruction chain.
- Cursor, [rules](https://cursor.com/docs/rules): repository instructions and scoped native rules are distinct routing options.
- GitHub, [custom-instruction support](https://docs.github.com/en/copilot/reference/custom-instructions-support): support differs by Copilot surface; a file that works in one surface is not proof for another.
- JetBrains, [project rules](https://www.jetbrains.com/help/ai-assistant/configure-project-rules.html): project rule placement and activation are host features.
- JetBrains, [Copilot agent](https://www.jetbrains.com/help/ai-assistant/copilot-agent.html): a third-party agent has its own integration constraints; do not assume every AI Assistant control applies.
- Git, [pull and fast-forward behavior](https://git-scm.com/docs/git-pull): fetching and integrating are different operations; fast-forward-only integration rejects divergence rather than resolving it by policy invention.

## Validation to perform

Use offline Git fixtures for the mechanical guard, including clean/stale/dirty/untracked/ahead/diverged/wrong-ref/detached states, multiple push destinations, unfinished operations and unavailable transport. Then run a real minor change from a cold environment with only the repository location and requested change. Record the actual host/model configuration when accessible. Repeat with stale state and a cold cache. Compare same-task acceptance, interventions, infrastructure retries and measured usage where available.

The helper fixtures do not establish IDE instruction delivery, successful environment setup, a low-cost model's behavior, physical hardware acceptance, cross-repository integration or deployment. Those layers remain open until independently executed.
